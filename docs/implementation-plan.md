# Agent Meter 实施方案

## 产品范围

开发独立的 macOS 软件，提供原生菜单栏 GUI 和 `agent-meter` CLI。登录、账号列表、凭据位置、当前选择、额度缓存均由软件管理；现有 shell 快捷指令仅用于定位本次验证的两个测试账号，不是产品依赖。

2026-09-16 已实现可运行的 **0.1.0 Preview**。构建与使用见 [README](../README.md)，本机实测记录不随公开源码发布。以下保留整体方案，当前支持范围见 README。

首版支持 Codex 官方网页登录、多账号额度与重置时间、官方重置卡数量、手动切换、官方桌面端重启切换。Claude 使用独立适配器，需先确认其多账号凭据与主动额度查询能力。

GUI 和 CLI 是同一产品的两个入口。点击账号和执行 `agent-meter switch <账号>` 调用同一个切换协调器。默认账号用于由软件启动的新 Codex CLI 会话；`agent-meter run codex --account <账号>` 可单次指定账号。普通、不经软件启动的 `codex` 命令如何接入，需要作为单独的兼容范围明确，不能虚报为全局切换成功。

## 实现结构

- `Agent Meter Preview.app`：AppKit 菜单栏常驻；管理窗口使用同一可执行文件的独立进程，关闭后退出。原生 Liquid Glass 使用 `NSGlassEffectView`。
- `AgentMeterCore`：共享 Swift 库，包含账号模型、官方客户端适配、查询、凭据存储和切换协调器。
- `agent-meter`：Swift CLI，与 GUI 使用同一核心库，通过跨进程锁保证操作互斥。预览版以原子文件更新和本机变更通知同步状态，无独立常驻账号服务。
- `agent-meter-bridge`：小型原生 Objective-C stdio 适配器，仅随受控官方桌面端运行，观察实际账号身份与活动任务；计入 30 MB 常驻总量。

为控制内存，菜单栏从有上限的缓存构造原生菜单，操作按需执行，不为每个账号常驻一个服务。Codex 查询、登录子进程按需启动，限制并发、设置超时并完整回收。

## 认证与查询

1. 添加账号时创建软件自己的独立账号环境，通过官方 `codex app-server` 发起浏览器登录。
2. 系统浏览器打开官方返回的登录地址，官方客户端处理认证回调和令牌刷新。
3. 读取实际身份后保存账号记录。预览版使用官方文件式凭据存储，独立目录 `0700`、凭据 `0600`；Keychain 隔离、同邮箱多工作空间识别与去重留待后续实现。
4. 每个账号使用独立且唯一的凭据来源。避免反复恢复静态凭据快照；刷新后必须保留最新状态。
5. 用 `account/rateLimits/read` 读取额度窗口、重置时间和 `rateLimitResetCredits.availableCount`。缺失、失败和数量为零是不同状态。

查询其他账号不改变当前账号。版本检测、能力检测、超时、退避和查询合并在适配器内统一处理。

## 切换协调

切换状态分为准备、等待任务结束、退出客户端、激活目标、重新启动、验证、完成/失败。持久化用户选择和各客户端实际状态，不能只保存一个“当前账号”标记。

1. 校验目标凭据有效，取得切换锁。
2. 识别要切换的桌面实例与运行任务。不能安全退出时等待或提示，禁止默认强杀工作中的客户端。
3. 正常退出需要切换的客户端，确认其认证子进程结束。
4. 以目标账号环境启动官方桌面端，并将同一账号设为软件 CLI 的默认选择。
5. 验证官方桌面端实际身份后才提交成功状态；失败时恢复可恢复的状态并明确显示未完成的目标。

本机验证证明了显式设置账号环境并正常退出/重启的路线可行，见验证报告。`CODEX_ELECTRON_USER_DATA_PATH`、`CODEX_CLI_PATH` 等桌面变量来自当前安装包，不能当作长期稳定的公开接口。生产适配必须做版本检测与回归测试；Python 转发器和 Chrome 调试端口仅用于本次验证，不能直接作为产品常驻组件。

预览版明确限制：只保证由本软件受控启动的官方桌面端使用所选账号，不改变 Dock/Finder 独立启动的账号选择。遇到非本软件启动的实例时，提示用户先手动退出，避免未知任务被终止。

## 原生界面与内存要求

界面使用系统 Liquid Glass 和原生组件，统一圆角、间距、字体、深浅色，响应减少透明度与减少动态效果设置。玻璃效果用于容器和操作区域，保持账号与额度文本清晰；控制效果层数和动画数量。

**空闲常驻内存上限为 30 MB，作为发布验收门槛。** 预览版的 10 条缓存账号记录、菜单/窗口各 10 次开关测试中，自有常驻进程合计约 25 MB；8 小时验收尚未完成。统一使用十进制 MB（30,000,000 字节）。

- 测量配置：Release / Apple Silicon、10 个账号。使用 physical footprint，合计主进程及全部常驻辅助进程；仍未退出的登录、查询子进程也计入。
- 测量状态：面板收起、操作结束后最多 60 秒内回到上限以内，并在后续空闲期间保持。既测首次启动，也测反复打开管理窗口、刷新和切换后的状态。
- 展开管理窗口、登录和查询期间的峰值另行记录，包含相关子进程；30 MB 是空闲常驻上限，不代表操作峰值。操作完成后必须回到上述上限。
- 用户运行的官方 Codex 桌面端和登录浏览器是独立应用，不计入 Agent Meter 的常驻预算；Agent Meter 的后台工作进程不能排除在统计外。
- 空闲时不保留 Codex 查询服务，不为每个账号设置常驻进程。额度显示使用有时效标记的缓存，刷新按需触发或使用低频、合并调度。

先实现最小 AppKit 菜单栏与原生面板，测量打开再关闭界面后的内存底线。SwiftUI 视图销毁不代表框架及缓存全部卸载；若实际常驻超标，调整界面实现或评估操作结束即退出的界面进程，并复测所有进程总量，不能通过提高预算放行。

窗口按需创建；结束展示时释放相关订阅、任务和重型视图。缓存只保留有上限的快照；输出流、重试队列、日志有大小与数量上限。使用合并刷新、有限并发和退避，避免重叠轮询。

防泄漏验收包含重复开关窗口、刷新、取消登录、切换失败、网络失败恢复和至少 8 小时运行。每轮操作结束后检查是否回到 30 MB 以内，同时对照预热后的内存基线检查持续增长，并检查引用环、残留子进程、文件描述符和未取消任务。使用 `footprint`、`vmmap`、`leaks`，在完整 Xcode 可用后补充 Instruments Allocations / Leaks。ARC 本身不等于无泄漏。

## 实施顺序

1. **桌面兼容性验证**：正常路径已实测；补充独立启动、认证过期、任务进行中、失败恢复等产品必需的边界。
2. **内存原型**：先测最小菜单栏、Liquid Glass 面板及反复开关后的占用，确认 30 MB 常驻预算可行，再扩充功能。
3. **独立核心与 CLI**：实现官方登录、账号持久化、查询、启动与切换状态机，持续检查内存预算。
4. **原生菜单栏与管理窗口**：接入同一核心，验证操作峰值和结束后的常驻占用。
5. **发布验收**：长期运行与泄漏检查、官方版本回归、签名和分发；再扩展 Claude。
